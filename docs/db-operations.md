# DB 운영·백업 전략 (operational procedures)

> '이음' 고택숙박(예약·결제·정산·개인정보 보유) MySQL8 운영 전략. codex 검토 기반.
> **용어 주의**: 여기 "절차/프로시저"는 **DB 운영 절차(백업·복구·유지보수 runbook)** 다.
> D17의 "업무 로직용 스토어드 프로시저 금지"와 별개 — 백업·유지보수 같은 DB/인프라 작업은 정상이며 필요하다.
> 배포/호스팅 미정 → **호스팅 무관(지금 확정)** 과 **호스팅 의존(나중)** 으로 구분. 결정주체 A(개발의뢰자)/B(큐어·인프라)/C(기술기본값).

## 전제 원칙
- 업무 로직은 Java, **운영 절차(백업/복구/보존/파기/유지보수/점검)는 별도 정의**.
- 운영 DB **수동 DDL 금지 → Flyway 롤포워드**(undo 대신 보정 마이그레이션).
- **백업 파일도 운영 DB와 동일한 민감정보**로 취급(암호화·접근통제).
- 예약·결제·정산·개인정보 변경은 분쟁·감사 대응 가능해야 함.

## 지금 확정/준비 가능 (호스팅 무관) — 우리 기준으로 채택

| 영역 | 채택 기준 |
| --- | --- |
| **백업 기본안** | **일일 풀백업 + binlog PITR + 35일 보관 + 암호화 + 오프사이트 + 분기 복구 리허설** (예약·결제 시스템 P0 최소선) |
| binlog | 활성화 필수, format `ROW`, 보존 7~35일 |
| 복구 원칙 | PITR 필수, 분기 1회 복구 리허설, 복구 후 checksum/row count 검증, 부분복구는 **임시 복구 DB**에서 추출 후 반영 |
| **DB 계정 분리** | `eeum_app`(DML 최소) · `eeum_flyway`(DDL/마이그레이션) · `eeum_backup`(백업 권한) · `eeum_readonly`(SELECT) · `eeum_admin`(개인별 DBA). **앱을 root/공유계정으로 연결 금지** |
| 보안 | TLS 전송암호화, at-rest 암호화, 백업 암호화, 민감컬럼(CI·계좌) 앱단 암호화 유지 |
| 파기 | 개인정보 파기 배치 + 증적(대상수/실행자/시각/결과). **백업 속 개인정보도 보존정책 대상** |
| 유지보수 | 슬로우쿼리 활성, 온라인 DDL(`ALGORITHM=INPLACE/INSTANT, LOCK=NONE`) 우선, 대형 DDL 사전 리허설, 로그/알림 등 대용량 테이블 파티셔닝 검토 |
| 모니터링 | 디스크(70/80/90%), 커넥션 사용률, 슬로우쿼리, 복제지연, **백업 성공/실패 즉시 알림**, binlog 용량, 장시간 트랜잭션 |
| 마이그레이션 절차 | 개발→스테이징(락·실행시간 검증)→운영(승인+사전 백업확인)→Flyway 적용→예약/결제/정산 점검→실패 시 롤포워드/롤백 |
| 위험 DDL 가드 | 대용량 타입변경/NOT NULL 추가/대량 인덱스/컬럼삭제/rename·drop/핵심테이블 변경 = 저트래픽 시간·승인·리허설 |

## 호스팅 정해진 뒤 (구현 방식 결정)
백업 구현(RDS 자동백업/스냅샷/XtraBackup) · PITR 설정(managed/binlog) · DR 구성(리전/센터/복제) · 암호화 구현(KMS/TDE/볼륨/키회전) ·
모니터링 도구(CloudWatch/Prometheus/Zabbix) · DB audit plugin/bastion 접근기록 · 페일오버(수동/자동·DNS·재연결) ·
백업 저장소(Object Storage/S3/NAS, 별도 계정·리전) · 운영 접근(Bastion/VPN/IAM) · 벤더 제약(RDS/NCP/온프레/Tibero·Oracle).

## 개발의뢰자(A)가 결정할 것 (목표치·정책)
| 항목 | 결정 |
| --- | --- |
| **RPO** | 장애 시 최대 데이터 손실 허용(권장 5~15분) |
| **RTO** | 복구 목표 시간(권장 1~4시간) |
| 백업 보관기간 | 35일 / 3개월 / 1년 (권장 단기 35일 + 월간 12개월) |
| 예약 데이터 보존기간 | 숙박 증빙 기준 (B와 함께) |
| 결제/정산 보존기간 | 회계·세무·감사 기준 (B와 함께) |
| 개인정보 보존/파기 | 목적달성 후 파기 또는 분리보관 (B 법무와) |
| DR 수준 | 백업기반 / warm standby / multi-region |
| 무중단 요구 | 야간 점검 가능 여부 |
| 접근감사 수준 | 관리자 쿼리 로그까지 남길지 |
| 호스팅 방향 | AWS/NCP/온프레/공공 DBMS |
| 비용 상한 | 백업·DR·모니터링·암호화 |

> 권장 출발선: **RPO 15분 / RTO 4시간 / 일일 풀백업+PITR / 35일+월간 12개월 / 암호화·오프사이트 / 분기 복구 리허설.**
> 호스팅이 매니지드(RDS 등)면 자동백업·PITR·스냅샷이 상당 부분 제공되어 구현 부담이 준다.

## 백엔드(앱)에서 지금 반영할 것 (코드/설정 차원)
- 멀티 DB 계정 전제 설정: 앱은 `eeum_app`(DML), 마이그레이션은 `eeum_flyway`(DDL) — Flyway 실행 계정/앱 계정 분리 가능하게 설정 구조 마련.
- 민감컬럼(CI·계좌·전화 등) **앱단 암호화**(이미 ERD 반영) + 마스킹.
- 파기/보존 배치 자리(스케줄러) — 호스팅 무관하게 앱에서 수행 가능.
- 슬로우쿼리·correlationId·감사로그(`AUDIT_LOG_INFO`/`LOGIN_LOG_INFO`/`EXTERNAL_CALL_LOG`)로 운영 추적성 확보(ERD §I).
