## 1. 인증 / 토큰 (P0)

| 항목 | 정할 것 | ▶권장 | 안 정하면 |
| --- | --- | --- | --- |
| Refresh 토큰 | access-only(testBoot) vs refresh 도입 | **refresh 도입 + access 단기(15~30분)** | 7일 access 탈취 시 회수 불가 |
| 로그아웃 | 무상태라 logout 처리 방법 | refresh를 DB/Redis에 저장→폐기, 또는 tokenVersion | 로그아웃 후에도 토큰 유효 |
| 토큰 저장소 | 완전 stateless vs DB vs Redis | 단일서버=DB, 다중=Redis | 강제 로그아웃 불가 |
| 동시 로그인 | 무제한 vs N개 vs 1개 | 일반 다중, 관리자 제한 | 계정 공유/추적 곤란 |
| JWT 서명키 | env 주입 + 교체(rotation) 정책 | env secret + keyId | 키 유출 시 전체 재로그인 |
| 비활성 계정 | 토큰만 신뢰 vs DB 상태 확인 | refresh 시 계정상태 재확인 | 탈퇴/정지 계정 계속 사용 |

> **⚠ M1 위험 수용(2026-06-11, codex 교차검토 확인)**: 탈퇴/정지/반려 후에도 **이미 발급된 access 토큰은 만료까지 최대 30분 유효**
> (refresh 시점에는 계정상태 재검증으로 차단됨, 탈퇴 시 refresh 세션 전체 회수됨).
> "즉시 차단"이 요구되면 **tokenVersion(JWT 클레임+DB 비교) 또는 denylist** 도입 필요 — 비밀번호 변경 시 무효화 정책과 함께 결정 대기.

## 5. API 표준 (P0)

| 항목 | 정할 것 | ▶권장 | 비고 |
| --- | --- | --- | --- |
| 실패 시 HTTP status | 항상 200 vs HTTP 의미 사용 | **HTTP status 의미 유지** + envelope body | 모니터링이 장애 감지 |
| ResultCode 카탈로그 | 코드 체계 표준 | 도메인 prefix + 의미코드 (예: `MEMBER_NOT_FOUND`) | 클라이언트 분기 |
| validation 오류 형식 | message만 vs fieldErrors | `result.fieldErrors[{field,message}]` | 폼 오류 표시 |
| 파일 다운로드 | envelope 예외 처리 | 다운로드는 binary 직접, 오류만 envelope | ★envelope 예외 명시 필요 |
| 페이지네이션 | 파라미터명/0-base여부 | `page`(1-base)/`pageSize`/`sort` 통일 | 화면별 불일치 |
| 정렬 | 자유 vs whitelist | **sort 컬럼 whitelist** | SQL injection |
| 검색 | 검색 DTO 표준 | Search DTO + 허용 연산자 제한 | 느린 쿼리 |
| API 버저닝 | 도입 여부 | 액션식이라 보통 생략 가능, 필요시 `/v1` | breaking change |

## 14. 고택숙박 — 요구사항정의서상 "큐어 협의/미정" 항목

> 공식 기획서 V1.0에 명시적으로 "큐어 확인/협의 필요/미정"으로 표기된 것들. **발주처(큐어)와 확정 필요**.
> 백엔드는 이들을 **정책 테이블 + 수동 운영**으로 시작하고(코드 하드코딩 금지), 확정 후 자동화.

| 영역 | 미정/협의 항목 | 백엔드 영향 | 우선 |
| --- | --- | --- | --- |
| 환불 | **8시간 환불정책 해석** (체크인 8h 전 vs 결제 후 8h?) + 위약금 배분 + 자동처리 가능여부 | 환불 계산 로직·정책테이블 | P0 |
| 정산 | 정산 로직 세부: 수수료율, **타OTA/네이버 금액 합산 여부**, 입금 D+5 확정, 부가세 | 정산 산출식·정책테이블 | P0 |
| 재고 | **객실 재고 단위** = "1실 단위" 확정 여부 (동일타입 수량 vs 실물 1개) | 재고 캘린더 모델 | P0 |
| 요금 | 요금 수정 **권한**(파트너 직접 vs 운영자 승인), 탄력요금제(비수기/성수기/할인) 범위 | 요금 권한·캘린더 | P0 |

## 16. DB 이식성 (배포 스펙 미정) — 고려사항

배포 서버/DB가 아직 미정. 개발은 **MySQL8**(개발서버, 스키마 `eeum`)이지만, 추후 다른 DB로 교체 가능성 있음.
(특히 공공/국가유산청 연계면 **Tibero·Oracle·PostgreSQL** 가능성.) 스펙 확정 시 변경작업 예정.

### ⚠ 솔직한 트레이드오프
- 우리는 **MyBatis(직접 SQL)** 을 쓴다(eGov 관례·testBoot 계승). JPA보다 **DB 이식성이 낮다** — SQL을 손으로 쓰므로 벤더 특화 구문이 섞이기 쉽다. 완전 이식은 그만큼 손이 더 간다(이건 감수한 선택).

### 지금 할 것 (과설계 없이 락인 최소화)
| 항목 | 방침 |
|---|---|
| 표준 SQL 우선 | `COALESCE`(IFNULL X), 표준 JOIN, 벤더 함수 지양 |
| 비즈니스 로직 | **(✅확정 D17)** DB 프로시저/트리거 대신 **Java(Service)에 둔다**. 이식성↑ |
| 벤더 특화 격리 | 불가피한 MySQL 전용 SQL은 매퍼에서 한 곳에 모으고 표시 |
| 설정 분리 | datasource URL/드라이버/방언은 application.yml + 환경변수 → 교체는 설정·의존성 변경 |
| ID 생성 | `AUTO_INCREMENT`(MySQL) ↔ `SEQUENCE`(Oracle/PG/Tibero) 차이 인지. 매퍼 `useGeneratedKeys` 사용부 식별 |
| 페이지네이션 | `LIMIT/OFFSET` 사용부 식별(타 DB는 구문 다름) |
| 타입 | ERD의 `DATETIME(6)`/`utf8mb4` 등은 MySQL 표기 → 타 DB 전환 시 매핑표 필요 |
| Flyway | 마이그레이션 SQL은 벤더별 → 전환 시 V스크립트 벤더 변형 필요(Flyway 벤더별 디렉터리 지원) |

### 나중에 (스펙 확정 시)
- 대상 DB 확정 → 드라이버/방언 교체, 벤더 특화 SQL·타입·ID생성·페이지네이션 변환, Flyway 스크립트 변형, 통합테스트 DB 교체.
- → **그래서 매퍼·DDL 작성 시 "이 부분이 MySQL 전용"임을 주석으로 표시**해두면 전환 비용이 크게 준다.
